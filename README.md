# AI Requirements Validator

Python-агент для статического ревью требований до разработки. Принимает Markdown или PDF с текстовым слоем, проверяет каждое выделенное положение и согласованность документа целиком. Записывает один и тот же отчёт на русском языке в Markdown и PDF.

## Подготовка

Нужен Python 3.10 или новее. Откройте терминал в корне клона.

**Windows PowerShell**

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

**macOS / Linux**

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
```

Получите ключ в [Google AI Studio](https://aistudio.google.com/api-keys). Для прогона без оплаты выберите проект на Free Tier и оставьте биллинг отключённым. Откройте локальный `.env` и укажите ключ после `GEMINI_API_KEY=`. Переменные окружения имеют приоритет перед этим файлом. `.env` игнорируется Git.

Модель по умолчанию — **Gemini 3.6 Flash** (`gemini-3.6-flash`). Доступ и квоты проверяйте в своём проекте. Другую модель Gemini с поддержкой структурированных ответов можно указать через `GEMINI_MODEL`. Агент передаёт извлечённый текст требований Gemini API. Проверяйте [условия обработки данных](https://aistudio.google.com/docs/terms) для используемого тарифа. [Карточка модели](https://aistudio.google.com/docs/models/gemini-3.6-flash) · [Тарифы](https://aistudio.google.com/docs/pricing#gemini-3.6-flash)

## Прогон

Документ организаторов передаётся как входной файл. Например, положите его в `docs/requirements.md` или укажите его текущий путь.

```powershell
.\.venv\Scripts\python.exe agent.py docs/requirements.md reports/report.md
```

```bash
.venv/bin/python agent.py docs/requirements.md reports/report.md
```

В уже активированном окружении эквивалентная команда — `python agent.py docs/requirements.md reports/report.md`. Второй аргумент задаёт путь к Markdown. Рядом агент создаёт `reports/report.pdf`. Для входного PDF замените первый аргумент на путь к `.pdf`. Если в пути есть пробелы, заключите его в кавычки.

Markdown читается в UTF-8. PDF должен содержать текстовый слой на каждой странице. Сканы нужно предварительно обработать OCR. Верхний предел — 100 000 символов извлечённого текста за один прогон. Для PDF-отчёта агент ищет Arial или Noto Sans на Windows, Arial на macOS либо DejaVu Sans на Linux. Если ни один шрифт не установлен, укажите `--font путь-к-шрифту.ttf` с кириллицей. При исчерпании квоты или сбое проверки агент завершает команду с ошибкой. Содержание отчёта может варьироваться между прогонами.

## Как проходит ревью

1. Агент нумерует строки входа, сохраняет соответствие страницам PDF и просит модель выделить отдельные обязанности, ограничения и условия приёмки. В каталоге есть исходный идентификатор, если он указан, а также идентификатор прогона, тип, краткая формулировка и цитата.
2. Модель получает источник целиком и проверяет каждое выделенное положение по 10 критериям. Оценки приходят группами до 12 положений, с отдельным вердиктом по каждому критерию.
3. Отдельный запрос проверяет весь набор по 6 критериям, включая пересечения между частями документа, интеграцией и критериями приёмки. Агент сопоставляет правила для общего события или состояния, проверяя область действия, исключения и приоритеты.
4. Python проверяет JSON, полноту вердиктов и дословность цитат после нормализации пробелов. Для заявленного противоречия требуются две отдельные цитаты. По итоговой структуре код формирует паспорт, таблицу, проверки, сводку и решение о готовности.

Критерии для положения — необходимость, уместность, однозначность, полнота, атомарность, выполнимость, проверяемость, корректность, единообразие и прослеживаемость. Для набора — полнота, согласованность, совместная выполнимость, проверяемость, ранжируемость и модифицируемость со связями. Это рабочие критерии, адаптированные из [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html), п. 5.2.5 и 5.2.6, и [IEEE 830-1998](https://standards.ieee.org/ieee/830/1222/), п. 4.3.

Критичный дефект блокирует однозначную разработку или приёмку ключевого сценария. Существенный меняет поведение или покрытие. Малый имеет локальное влияние. Отчёт считает карточки дефектов и приводит приоритетные исправления. Для каждой карточки указаны источник, последствие и предложение автору требований.

При сдаче приложите исходный документ и оба файла отчёта рядом со ссылкой на репозиторий.
